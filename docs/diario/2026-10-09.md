# Diario de desarrollo — 2026-10-09

## Contexto

La fase 2 estaba cerrada (0.4.0). El ROADMAP dejaba como primer ítem de la fase 3 la API de carga de datasets.

## Trabajo realizado

| Área | Detalle |
|------|---------|
| Contrato | `POST /datasets` recibe un CSV multipart, objetivo opcional y bandera `apply`. |
| Informe | La carga reutiliza `analyze_frame`: perfil, issues, plan, objetivo y modelado. |
| Consulta | `GET /datasets` lista metadatos; `GET /datasets/{id}` devuelve el informe; `GET /datasets/{id}/cleaned` expone el CSV si el plan se aplicó. |
| Validación | Rechazo de no-CSV, archivo vacío, más de 2 MB, codificación distinta de UTF-8 y filas con distinto número de campos. |
| Estado | El registro es en memoria. No se persiste entre procesos. |
| Pruebas | `tests/test_api.py`: carga y recuperación, plan aplicado, rechazos y salud. |

## Decisiones

- Se extrajo `analyze_frame` para que la CLI y la API compartan el mismo informe.
- No se implementó persistencia: es el tercer ítem de la fase 3 y no debe mezclarse con el contrato de carga.
- No se implementó la interfaz de revisión del plan: depende de que la API de carga exista y queda como siguiente entregable.

## Resultado de validación

- `pytest`: 17 pruebas aprobadas.

## Próximo paso recomendado

Interfaz para revisar issues y aceptar el plan de limpieza, consumiendo `GET /datasets/{id}` y una acción explícita de aceptación.
